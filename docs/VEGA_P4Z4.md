# VEGA P4Z4 agent («Пароль? Не обязательно»)

`vega_p4z4/` — четвёртый автономный экспорт для тестовой системы VEGA и
развитие SQLi-домена [P4Z2](VEGA_P4Z2.md): форма входа подставляет в
SQL-запрос **и логин, и пароль как есть**, но служба пускает в кабинет
**только администратора** — первый совпавший пользователь может быть рядовым.
Агент входит именно админской строкой, забирает флаг (в том числе спрятанный
в отдельной таблице БД) и записывает точное значение в
`$VEGA_CTF_ARTIFACT_DIR/flag.txt`. Экспорт не меняет SAST/DAST pipeline и
поставляется отдельным архивом без зависимостей (только стандартная
библиотека Python).

Все пять экспортов собираются одной командой:

```powershell
python scripts/build_vega.py
```

Результат: `dist/security-agent-vega.zip` (базовый агент),
`dist/security-agent-p3z2.zip`, `dist/security-agent-p3z3.zip`,
`dist/security-agent-p4z2.zip` и `dist/security-agent-p4z4.zip` (P4Z4). В
корне каждого архива находятся ровно `run.sh`, `agent.json`, `agent.py`,
`strategy.md`.

## Архитектура

Тот же LLM-цикл с инструментами (54 шага, окно 18 сообщений, дедлайн 580 c),
что и у остальных агентов платформы; finish-валидация против выдумывания,
graceful-фолбэки. Поверх базового SQLi-домена P4Z4 несёт **пять раундов
соревновательных итераций** (стратегия `vega_p4z4/strategy.md`, регресс
14→16 сценариев на автономных копиях):

1. **Полная матрица без ранней остановки.** Первый «успех» — обычно рядовой
   юзер («Доступ в кабинет только для администратора»): матрица проходит
   целиком, успешные хиты собираются (дедуп по sha1, cap 6 + cookie), обрыв —
   только по flag-shaped значению.
2. **Phase 1b — пустой пароль** и **Phase 2 — парольная матрица** (14
   payload'ов × логины из рекогносцировки + admin/margo/user): легенда прямо
   указывает на незаполненное поле пароля.
3. **Админ-приоритизация** (`_admin_flavoured`): хиты и сессии сортируются —
   admin/администратор в payload или ответе идут первыми; Phase 4 проходит
   до 3 сессий в порядке приоритета.
4. **Phase 0 — рекогносцировка материалов** (`_source_secrets`): INSERT/tuple/
   dict-паттерны и .env/yaml-присваивания дают реальные логины/пароли; для
   каждого найденного имени строятся таргетированные payload'ы
   (`<name>'--`, `' OR username='<name>' --`).
5. **Скрытые поля формы воспроизводятся**: `parse_form` собирает hidden/submit
   поля с значениями и подставляет их в каждый запрос — CSRF-защита больше не
   отбрасывает матрицу; главная страница — валидный кандидат на форму входа
   (фикс `distinct()`).
6. **Phase 5 — UNION-извлечение данных** (`_union_extract`): если флаг не
   появился ни в одном ответе, агент закрывает инъекционный запрос и
   достраивает `UNION SELECT`: перечисление схемы (sqlite_master /
   information_schema / pg_tables), дамп flag-bearing таблиц через подзапросы
   (переживают неизвестное число колонок внешнего SELECT), фолбэк-угадывание
   `flags/secrets/config/tokens`.
7. **Формат-независимый сбор секретов** (`SECRET_LINE_RX`): строки
   `Флаг: …`, `Секрет = …`, `Ваш токен доступа: …` из живых ответов — даже
   без формата `vega{...}`; ранжирование: сначала vega-формат, значения из
   админ-ответов — выше приманок.
8. **Надёжность**: HTTP-инструменты не бросают исключений; retry после
   429/503 и пауза 20 мс между запросами; `resolve_target` читает реальный
   URL из instruction.md (env-URL, затем URL из материалов, bind-адреса —
   последними); auto-pilot запускает `login_probe` сам, если модель
   зациклилась; decoy guard в `finish` отклоняет значение, встреченное только
   в не-админских ответах (до двух раз), и подсказывает админского кандидата;
   аварийный обработчик `__main__` **никогда не перезаписывает непустой
   flag.txt** и всегда завершает процесс с кодом 0; рядом с flag.txt пишется
   `report.txt` (target, tried_finish, flag_contexts, union_schema_blob,
   превью последних ответов) — Wrong Answer диагностируется по артефактам.

Payload-матрица: admin-таргетинг (`admin'--`, `' OR username='admin' -- `,
`' OR role='admin' -- `, `' OR id=1 -- `), синонимы role-колонки
(`is_admin`, `level`, `status`, `priv`, `user_type`, `grp` — числовые и
строковые), конкатенация при фильтре слова admin (`'adm'||'in'`), `/**/` и
tab вместо пробелов, двойные кавычки, скобки, LIMIT, EXISTS и
UNION-фабрикация админ-строки (1–5 колонок, числовая роль).

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| `inventory`, `read_file`, `grep_files` | разведка материалов: точная конструкция запроса, проверка роли, сид-данные |
| `http` | GET с авто-прикреплением cookie сессии; тело в preview |
| `http_batch` | до 60 GET-путей параллельно, дедуп по sha1 |
| `http_post` | POST-форма без auto-follow: статус, Set-Cookie, Location; cookie глобально |
| `login_probe` | главный инструмент: форма → baseline → полная SQLi-матрица (Phase 0–3) → сессии → Phase 4 → Phase 5 UNION |
| `decode` | base64/hex/url (запоминается как evidence, если значение было в ответах) |
| `finish` | завершение; значение принимается только из живых ответов, decoy guard проверяет админ-контекст |

## Отличия от исходного P4Z4-агента (харденинг-дельты интеграции)

Код перенесён 1:1 (AST-сверка `scripts/ast_diff_p4z4.py`; единственное
исключение — сохранённый как есть неиспользуемый кортеж `hits, definite` с
`noqa`) и приведён к стандартам проекта с теми же тремя харденинг-правками,
что и у остальных агентов:

- файловые операции остаются внутри canonical `MATERIALS`: guard использует
  `realpath` и строгий префикс — symlink- и sibling-directory escape
  отклоняются;
- артефакт (`flag.txt`) пишется атомарно (временный файл + `os.replace`) —
  важно именно для P4Z4: его round-4 чинит затирание верного флага, атомарная
  запись убирает и гонку «читатель увидел полфайла»;
- недостающая конфигурация LLM даёт одну безопасную ошибку
  (`VEGA model gateway is not configured: …`) вместо сырого traceback.

Плюс платформенная дельта v2: base64-автодекод флагов в `_response_record`
(`decode_b64_flags`, импорт `base64` на верхний уровень) — флаг, спрятанный
в base64-блобе честного ответа, попадает в EVIDENCE автоматически.

## Проверка

Offline-проверки не используют сеть: уязвимый сервис реализован в памяти на
**настоящем sqlite3** с уязвимой string-concat сборкой запроса и ролевым
гейтом; модель скриптуется; `_probe_url` заглушен (кроме теста
`resolve_target`).

```powershell
pytest -q tests/test_vega_p4z4.py
```

36 тестов: контракт архива (сборка `build_p4z4`, manifest, атомарная запись,
hardened guard, crash-guard в исходнике), path-guard
(escape/sibling/symlink), безопасная ошибка конфигурации, `resolve_target`
без ответов, контракты разбора реплик, `unwrap_body`, FLAG_RX +
SECRET_LINE_RX, redirect-guard'ы, evidence/кэш, захват cookie без следования
за 302, `decode`, v2 base64-автодекод, парсинг формы с hidden-полями,
`form_field_pair`, `_source_secrets` (INSERT + .env), `_better_candidate`,
сценарии m1–m16:

- **m1** ролевой гейт: `' OR 1=1 --` даёт рядового юзера — матрица доходит до
  admin-payload'ов (первый успех собран, но не завершает скан);
- **m2** сессия: admin → 302+cookie → /dashboard → флаг; не-админ получает
  «Доступ запрещён» без сессии;
- **m3** фильтр слова admin → конкатенация `'adm'||'in'`;
- **m4** GET-форма;
- **m5** двухшаговая сессия (/dashboard → /admin/flag);
- **m6** нестандартный формат (`Ваш токен доступа: …` через SECRET_LINE_RX);
- **m7** приманка: decoy из ответа рядовому юзеру уходит в конец ранжирования;
- **m8** форма на главной + скрытый CSRF: без токена вся матрица 403, с
  воспроизведением hidden-поля — успех;
- **m9** админ зовётся не admin (rosello): Phase 0 находит креды в материалах;
- **m10/m11** UNION-извлечение: флаг в отдельной таблице `secrets` — admin
  входит, но флаг достаёт только Phase 5 (в т.ч. blind без админ-строки);
- **m15** логин санитизируется — инъекция только через парольную матрицу;
- **m16** колонка `is_admin INTEGER`, админ последним в таблице — побеждает
  `' OR is_admin=1 --`;

плюс отчёт при полном промахе и четыре сквозных сценария: верифицированный
finish (exit 0 + report.txt), decoy guard (finish с приманкой → подсказка →
верный флаг), auto-pilot (модель-«бесполезный цикл» → агент сам пишет
ранжированного кандидата) и `resolve_target` (URL из instruction.md,
env не задан).

> Минимальный `agent.json` (`format: vega-agent-harness`) следует подтвердить
> реальным VEGA validator до публикации архива для конкретной инсталляции.
