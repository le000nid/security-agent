# VEGA P4Z2 agent («Отчёт, которому не верят»)

`vega_p4z2/` — третий автономный экспорт для тестовой системы VEGA и первый
представитель раунда P4: агент обходит SQL-инъекцию в форме входа на
`http://target:8000` (логин подставляется в SQL-запрос как есть), входит в
кабинет без пароля, забирает флаг и записывает его точное значение в
`$VEGA_CTF_ARTIFACT_DIR/flag.txt`. Как и [базовый VEGA adapter](VEGA.md) и
агенты [P3Z2](VEGA_P3Z2.md)/[P3Z3](VEGA_P3Z3.md), он не меняет SAST/DAST
pipeline, benchmark или правила основного приложения и поставляется отдельным
архивом без зависимостей (только стандартная библиотека Python).

Все четыре экспорта собираются одной командой:

```powershell
python scripts/build_vega.py
```

Результат: `dist/security-agent-vega.zip` (базовый агент),
`dist/security-agent-p3z2.zip`, `dist/security-agent-p3z3.zip` и
`dist/security-agent-p4z2.zip` (P4Z2). В корне каждого архива находятся ровно
`run.sh`, `agent.json`, `agent.py`, `strategy.md`.

## Архитектура

Та же архитектура, что выиграла P2Z1/P2Z3/P2Z4/P2Z5/P3Z2/P3Z3: компактный
LLM-цикл с инструментами (54 шага, окно 18 сообщений, дедлайн 580 c), где
модель расследует, инструменты исполняют, а результат `finish` проверяется по
живым HTTP-ответам (`EVIDENCE["http"]`).

```text
instruction.md + materials -> LLM (54 шага, дедлайн 580 c)
        -> одно JSON-действие -> инструмент -> наблюдение -> LLM ...
        -> finish -> проверка по EVIDENCE -> flag.txt
```

Доменное отличие от P3Z2/P3Z3: цель — не файловая служба, а форма входа.
Ключевые новые механизмы:

- **`http_post`** — POST-формы; редирект НЕ следует автоматически: статус,
  `Set-Cookie` и `Location` возвращаются агенту как данные. Захваченная
  cookie сессии сохраняется глобально (`SESSION_COOKIE`) и автоматически
  прикрепляется ко всем последующим запросам.
- **`login_probe`** — главный инструмент: находит форму входа (GET `/`,
  `/login`, `/admin`, `/signin`… c парсингом `<form action= method=>` и имён
  `<input>`, CSRF-поля отбрасываются), шлёт baseline с заведомо неверными
  кредами, затем матрицу 30 username-payload'ов × варианты password (Phase 1
  — классика с `password=x`, Phase 2 — инъекция в password, Phase 3 —
  GET-вариант того же endpoint'а). Детекция успеха: flag-shaped значение ИЛИ
  (тело ≠ baseline) И (маркер welcome/dashboard/flag ИЛИ set-cookie ИЛИ
  location), с отсечением «Неверный логин».
- **следование сессии** — после успешного входа агент идёт по `Location` и
  dashboard-путям с cookie, парсит `href` с аутентифицированных страниц и
  догружает интересные ссылки (двухшаговый сценарий `/dashboard` →
  `/admin/flag`).

Матрица payload'ов покрывает: закрытие кавычки с OR-условием (`' OR 1=1 -- `,
`' OR '1'='1`, `') OR ('1'='1`), комментирование хвоста (`admin'--`, `admin' #`,
`admin'-- -`), обход фильтра пробелов/слов (`/**/` вместо пробелов, tab,
`admin'--` без OR вовсе), двойную кавычку (`" OR 1=1 -- `), конкатенацию
(`' || '1'='1`) и `EXISTS`-варианты.

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| `inventory`, `read_file`, `grep_files` | разведка по materials: точная конструкция SQL-запроса, имена полей, endpoint |
| `http` | GET-запрос с авто-прикреплением cookie сессии; тело в preview |
| `http_batch` | до 60 GET-путей параллельно, дедуп по sha1 |
| `http_post` | POST-форма без auto-follow: статус, Set-Cookie, Location, тело; cookie запоминается глобально |
| `login_probe` | главный инструмент: форма → baseline → матрица SQLi → захват сессии → dashboard/ссылки за флагом |
| `decode` | base64/hex/url (декодированное запоминается как evidence, если исходное значение было в ответах) |
| `finish` | завершение; флаг принимается только если он содержится в сохранённых живых ответах |

`unwrap_body` разворачивает JSON-обёртки и HTML `<pre>`. Платформенное
расширение v2 включено: флаги, спрятанные в base64-блобе внутри честного
ответа (≥24 символов), декодируются автоматически и попадают в EVIDENCE.

## Отличия от исходного P4Z2-агента (харденинг-дельты интеграции)

Код логики перенесён 1:1 (проверено AST-сравнением: `scripts/ast_diff_p4z2.py`)
и приведён к стандартам проекта (Ruff-форматирование, сортировка импортов) с
теми же тремя харденинг-правками, что и для P3Z2/P3Z3:

- файловые операции остаются внутри canonical `MATERIALS`: guard использует
  `realpath` и строгий префикс — symlink- и sibling-directory escape
  отклоняются;
- артефакт (`flag.txt`) пишется атомарно (временный файл + `os.replace`);
- недостающая конфигурация LLM даёт одну безопасную ошибку
  (`VEGA model gateway is not configured: …`) вместо сырого traceback.

Плюс две платформенные дельты: v2 base64-автодекод флагов в
`_response_record` (и импорт `base64` на верхний уровень) и чистка
случайного дубля `/cabinet` в `DASH_PATHS`.

Ограничения поверхности: HTTP ограничен `VEGA_TARGET_URL`, redirects только
внутри того же scheme/host/port (`GuardedRedirect`), POST выполняется через
opener без следования за редиректами (`NoRedirect`); цикл ограничен
`VEGA_AGENT_MAX_STEPS` (54) и дедлайном 580 секунд; stderr не содержит
содержимого реплик и значений флага (только счётчики: форма, попытки, хиты).

## Проверка

Offline-проверки не используют сеть: уязвимый сервис реализован в памяти на
**настоящем sqlite3** с уязвимой string-concat сборкой запроса — кавычки,
комментарии и OR-тавтологии работают аутентично; модель скриптуется.

```powershell
pytest -q tests/test_vega_p4z2.py
```

27 тестов: контракт архива (сборка `build_p4z2`, manifest, атомарная запись и
hardened guard в исходнике), path-guard (escape/sibling/symlink), контракты
разбора реплик (`action_from_text` во всех форматах), `unwrap_body`,
flag-shaped regex, redirect-guard (`GuardedRedirect`/`NoRedirect`),
безопасная ошибка конфигурации, evidence/кэш, `http_batch` с дедупом,
захват cookie без следования за 302 и авто-прикрепление к следующему GET,
`decode` (запоминание только значений из evidence), v2 base64-автодекод
(юнит + через `http_post`), парсинг формы (action/method/поля + фильтр CSRF),
выбор пары полей, `grep_files`, пять сценариев m1–m5:

- **m1**: флаг прямо в ответе на `' OR 1=1 -- ` (flag_direct);
- **m2**: 302 + Set-Cookie → `/dashboard` → флаг через следование сессии;
- **m3**: фильтр пробелов и слова OR → побеждает `admin'--`;
- **m4**: GET-форма — матрица уходит query-параметрами;
- **m5**: `/dashboard` без флага → ссылка `/admin/flag` (двухшаговое
  следование);

плюс отчёт при неудаче (baseline/hits без ложного успеха) и три сквозных
сценария цикла: `login_probe → finish verified`, отказ выдуманному флагу с
последующим подтверждённым завершением и graceful-фолбэк на лучший
flag-shaped кандидат из EVIDENCE.

Сценарии m1–m5 из `strategy.md` выполнены на исходном пакетированном агенте
до интеграции; интегрированный агент отличается тремя харденинг-правками и
двумя платформенными дельтами, покрытыми офлайн-тестами.

> Минимальный `agent.json` (`format: vega-agent-harness`) следует подтвердить
> реальным VEGA validator до публикации архива для конкретной инсталляции.
