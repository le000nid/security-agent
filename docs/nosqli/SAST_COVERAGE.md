# NoSQLi: расширение SAST

В третьем этапе расширены правила Semgrep и добавлена матрица из 80 примеров:
40 на JavaScript и 40 на TypeScript. В каждом языке 20 опасных и 20 безопасных случаев.
Это примеры для статического анализа, а не ещё один работающий сайт.

## Запуск

Из корня проекта, нужен работающий Docker:

```bash
bash scripts/check-nosqli-sast.sh
```

Скрипт собирает агента, запускает настоящий Semgrep через `agent scan`
и сверяет общий отчёт с инвентарём примеров. Поднимать MongoDB для этого
SAST-набора не требуется.

Ожидается 40 находок и финальная строка:

```text
NoSQLi SAST matrix acceptance passed: 40 dangerous and 40 safe cases.
```

Запуск агента отдельно:

```bash
export AGENT_UID="$(id -u)"
export AGENT_GID="$(id -g)"

docker compose --profile agent run --rm --no-deps \
  agent scan --benchmark nosqli-sast-matrix --mode sast --no-llm
```

Запись `nosqli-sast-matrix` доступна и в списке наборов веб-интерфейса
после пересборки его образа. Результат сохраняется в обычных
`report.md`, `findings.json` и `summary.json`.

## Что изменилось в правилах

| Правило | Что ищет | Что проверено дополнительно |
|---|---|---|
| `javascript-nosqli-tainted-where` | Ввод в выражении `$where` | Конкатенация, шаблонная строка, промежуточная переменная, доступ через скобки, `countDocuments` |
| `javascript-nosqli-scalar-operator` | Непроверенное значение поля фильтра | Вложенное поле, псевдоним переменной, скобки, заранее собранный `const`-фильтр с возвратом запроса, `countDocuments`, второй аргумент `distinct` |
| `javascript-nosqli-untrusted-filter` | Пользовательский фильтр целиком | Поля `filter`, `criteria`, `selector`; `JSON.parse`, spread, `Object.assign`, копирование через JSON |
| `javascript-nosqli-untrusted-pipeline` | Пользовательские данные в aggregation pipeline | Pipeline целиком, декодирование JSON, пользовательский `$match`, spread и промежуточная переменная |

Aggregation pipeline — последовательность шагов обработки данных MongoDB.
Например, `$match` отбирает записи. Если принять такой фильтр или всю
последовательность от пользователя без ограничений, он сможет изменить
логику выборки. Новое правило отмечает этот поток данных для проверки.
Само наличие `aggregate()` не считается ошибкой.

Правила не выполняют запросы. Методы записи в БД и проверки поведения
aggregation pipeline через DAST в этом этапе не добавлялись.

## Два важных различия

```javascript
const sku = String(req.body.sku);
collection.find({ sku });
```

Здесь `String()` превращает объект с оператором в строку — объект уже не
попадёт в фильтр как оператор. Это защита от данного механизма, но не
полная бизнес-валидация: отдельно нужны длина, формат и допустимые значения.

```javascript
const expression = "this.product == " + String(req.params.id);
collection.find({ $where: expression });
```

Здесь `String()` не экранирует код. Ввод всё ещё становится частью выражения.
Правило `$where` продолжает срабатывать. Числовое преобразование учитывается
отдельно; предпочтительнее отказаться от конструирования `$where`.

В TypeScript запись `value as string` тоже не проверяет данные во время
выполнения. Такой пример должен давать находку, в отличие от `String(value)`
в обычном поле фильтра.

## Как устроена проверка качества

`config/nosqli-sast-cases.json` перечисляет каждый пример: файл, функцию,
правило и ожидаемое наличие находки.

В исходниках перед проверяемой строкой стоит:

```javascript
// ruleid: javascript-nosqli-scalar-operator
return collection.find({ sku: req.body.sku });
```

Для безопасных примеров используется `// ok: ...`.
В случае заранее собранного фильтра метка стоит у присваивания поля:
Semgrep указывает место, где опасное значение вошло в объект.

Проверяющий модуль сверяет:

- состав файлов JavaScript и TypeScript и отсутствие ошибок сканера;
- наличие всех функций и соответствие аннотаций инвентарю;
- правило и точную строку каждой находки;
- отсутствие пропусков, дубликатов и неожиданных находок;
- сохранение тех же мест в общих JSON- и Markdown-отчётах;
- отсутствие вызовов LLM.

На этом наборе по 10 опасных и 10 безопасных примеров для каждого правила.
Часть примеров повторяет одну конструкцию в двух языках: это проверка
поддержки JS и TS, а не 80 разных механизмов NoSQLi.

Сравнение настоящим Semgrep 1.120.0 на одной и той же матрице:

| Версия правил | Найдено ожидаемых мест из 40 | Неожиданные находки |
|---|---:|---:|
| До третьего этапа | 10 | 2 |
| После третьего этапа | 40 | 0 |

Эта таблица относится только к данному корпусу. Она не измеряет точность
сканирования произвольных проектов.

## Ограничения

- Проверяется поток данных внутри функции. Произвольные цепочки своих
  функций и переходы между файлами не заявляются как покрытые.
- Источники моделируют обращения к `body`, `query`, `params`; автоматически
  распознавать все фреймворки и пользовательские обёртки правила не умеют.
- Имена получателя `find`/`aggregate` не доказывают, что используется MongoDB.
  Поэтому находки имеют среднюю уверенность и требуют проверки контекста.
- Полный фильтр отслеживается для полей `filter`, `criteria`, `selector`;
  pipeline — для этих полей и `pipeline`. Другие схемы требуют доработки правила.
- Не все формы сборки объекта покрыты. Дополнительный случай заранее
  собранного поля проверен для `const filter = {...}; ...; return query(filter)`.
  Сложные последующие изменения полей объекта требуют ручной проверки;
  структурный шаблон может отметить исходное присваивание, даже если оно
  было исправлено более поздней операцией.
- Пользовательские функции валидации и проверка типов через сложные условия
  могут не распознаваться. Произвольная функция с именем `validate()`
  не объявляется безопасной автоматически.
- `String`, `Number`, `parseInt`, `parseFloat` предполагаются стандартными
  функциями. Их переопределение в проекте требует отдельного анализа.
- SAST-находка — подозрительный путь данных. Работоспособность конкретной
  атаки подтверждается отдельно через DAST.

## Где смотреть код

| Файл | Назначение |
|---|---|
| `config/semgrep.yaml` | Три расширенных правила и новое правило pipeline |
| `targets/nosqli-variants/javascript/` | Четыре JS-файла с опасными и безопасными функциями |
| `targets/nosqli-variants/typescript/` | Четыре TS-файла; включая небезопасное приведение `as string` |
| `config/nosqli-sast-cases.json` | Инвентарь всех примеров |
| `benchmark/verify_nosqli_sast_matrix.py` | Сверка инвентаря, реального сканирования и общего отчёта |
| `benchmark/verify_nosqli_sast.py` | Общая проверка точных мест; теперь учитывает `.js` и `.ts` |
| `tests/nosqli/test_sast_matrix.py` | Тесты ошибок инвентаря, пропусков, ложных находок и отчётов |
| `scripts/check-nosqli-sast.sh` | Запуск третьего этапа одной командой |

После изменения правил образ агента нужно пересобрать.
Первый и второй этапы остаются доступны через свои прежние скрипты.
