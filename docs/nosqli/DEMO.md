# Как показать NoSQLi-блок

## Что сказать

Я сделал блок проверок NoSQL-инъекций со стороны кода и работающего API.
Сначала добавил учебный API с настоящей MongoDB и безопасными парами.
Потом сделал HTTP-проверку, которую можно настроить под другой JSON API,
и расширил правила Semgrep для JavaScript и TypeScript.
Результаты проходят через общий запуск агента, отчёты и веб-API проекта.

SAST показывает подозрительный путь пользовательских данных в запрос.
DAST проверяет поведение: изменилось ли содержимое выборки после передачи
оператора. Это разные доказательства, они дополняют друг друга.

## Что открыть

1. `targets/nosqli-lab/src/routes/operator.js`: опасный запрос и безопасная пара.
2. `config/nosqli-profiles.yaml`: контракт первого и второго API.
3. `app/nosqli/scanner.py`: четыре запроса и сравнение записей.
4. `config/semgrep.yaml`: четыре NoSQL-правила.
5. `targets/nosqli-variants/typescript/scalar.ts`: почему `as string`
   не проверяет ввод во время выполнения.
6. Полученный `report.md`: реальная находка и её доказательство.

## Как показать результат

Один наглядный DAST-запуск без LLM:

```bash
bash run.sh scan --benchmark nosqli-profile-inventory --mode dast --no-llm
```

Безопасная пара:

```bash
bash run.sh scan --benchmark nosqli-profile-inventory-safe --mode dast --no-llm
```

Ожидаем две находки на опасных маршрутах POST/GET и ноль на безопасных.
В этой интеграционной версии второй API доступен на порту 3008.

Матрица SAST:

```bash
bash scripts/check-nosqli-sast.sh
```

40 опасных и 40 безопасных примеров — это проверка качества правил
на известном наборе. Это не 80 разных видов инъекций.

## Что не обещать

Не говорить, что агент проверяет все виды NoSQLi на любом сайте.
HTTP-проверке нужен известный JSON-контракт и стабильные данные.
SAST имеет ограничения по формам кода и переходам между функциями.
Отсутствие находок не является доказательством безопасности всего приложения.
