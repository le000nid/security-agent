# NoSQLi: проверка по настройкам API

Раньше шаблоны знали конкретные маршруты и ID товаров нашего стенда.
Теперь проверка получает описание API из `config/nosqli-profiles.yaml`.
Меняются настройки, а код сравнения остаётся тем же.

Пока переносится один механизм: объект с оператором вместо обычной строки.
Это не поиск всех вариантов NoSQLi и не автоматическое изучение любого сайта.

## Запуск

Из корня проекта, в Bash. Нужен работающий Docker с Compose.

```bash
bash scripts/check-nosqli-portable.sh
```

Скрипт собирает агента и API, запускает MongoDB, проверяет Node.js-код
и выполняет четыре запуска агента без LLM:

| Набор | Что проверяем | Ожидается |
|---|---|---|
| `nosqli-profile-catalog` | Первый API, поле `sku`, POST | 1 находка |
| `nosqli-profile-catalog-safe` | Его безопасная пара | 0 находок, оператор отклонён |
| `nosqli-profile-inventory` | Второй API, вложенное поле, POST и GET | 2 находки |
| `nosqli-profile-inventory-safe` | Его безопасные пары | 0 находок, операторы отклонены |

Это три срабатывания одного механизма на двух API, а не три новых вида уязвимостей.
Во втором API используется другая коллекция настоящей MongoDB.

Каждый запуск проверяется сразу после завершения: находки, статусы запросов,
контрольные ответы, общий отчёт и отсутствие обращений к LLM.
Для обоих наборов тестов MongoDB должна быть доступна: пропуск этих тестов
при запуске через скрипт не предусмотрен конфигурацией окружения.

Первый этап проверяется отдельно:

```bash
bash scripts/check-nosqli.sh
```

Его ожидаемый результат прежний: 3 SAST + 3 DAST в FULL-запуске.

## Что происходит внутри

На один профиль отправляются четыре запроса:

1. Обычное значение — должны вернуться подходящие записи.
2. Объект с оператором — проверяем, расширилась ли выборка.
3. Случайная строка, которой не должно быть в базе — ждём пустую выборку.
4. Снова обычное значение — проверяем стабильность исходного результата.

Находка появляется, если второй ответ включает исходные записи и новые записи
с другим значением проверяемого поля. Контрольный ответ должен быть пустым,
а повтор исходного запроса — возвращать те же ID и значения.
Сравнивается содержимое полей и состав записей, а не длина ответа.
Порядок записей значения не имеет.

Если сервер возвращает 400 или 422 на объект с оператором, результат — `rejected`.
Если нужной разницы нет — `not_detected`. Эти результаты не доказывают
безопасность всего приложения.

Ошибки HTTP, неправильный JSON, неверная структура или нестабильный исходный
результат дают `inconclusive`: проверка не смогла сделать вывод.
В общем запуске появится предупреждение. Подтверждённые находки других
профилей сохраняются.

## Пример профиля

```yaml
- id: inventory-post
  method: POST
  path: /v2/inventory/search
  field_path: [selection, code]
  baseline: WIDGET-42
  records_path: [payload, items]
  id_path: [itemId]
  value_path: [code]
```

| Поле | Что означает |
|---|---|
| `id` | Имя профиля; его выбирает запись в `config/benchmarks.yaml` |
| `method` | POST с JSON-телом или GET с JSON в одном параметре |
| `path` | Путь на выбранном сервере |
| `field_path` | Куда положить проверяемое значение: здесь `selection.code` |
| `baseline` | Существующее обычное значение для исходного запроса |
| `records_path` | Где в JSON-ответе находится массив записей |
| `id_path` | Поле с уникальным строковым или целочисленным ID записи |
| `value_path` | Поле записи, соответствующее проверяемому значению |
| `query_parameter` | Для GET: имя параметра, содержащего JSON; по умолчанию `filter` |

Пример тела: `{"selection":{"code":"WIDGET-42"}}`.
Пример ответа: `{"payload":{"items":[{"itemId":"warehouse-201","code":"WIDGET-42"}]}}`.
ID записей в профиле не задаются. Для GET-профиля этого API используется
параметр `criteria`, содержащий такой же JSON.

Чтобы добавить свой API, сначала выясни его контракт и выбери читающий маршрут.
Добавь профиль и запись benchmark с `nosqli_profiles: [имя-профиля]`.
Настройки хранятся в проекте; через чат или веб-запрос нельзя передать
произвольный профиль. У проекта сохраняется ограничение на локальные цели.
После изменения конфигурации пересобери образ агента.

## Где результат

```bash
docker compose -f docker-compose.yml -f docker-compose.nosqli.yml \
  --profile agent run --rm --no-deps \
  agent scan --benchmark nosqli-profile-inventory --mode dast --no-llm
```

Путь к запуску выводится в терминале. Внутри него:

- `reports/report.md` — общий читаемый отчёт;
- `reports/findings.json` — общие находки, инструмент `nosqli-http`;
- `reports/summary.json` — итог, выбранные профили и предупреждения;
- `logs/raw_nosqli.json` — статусы запросов, количество записей и хеши их состава.

Тексты записей и учётные данные в этот лог не копируются.
Хеш позволяет сравнить состав ответов, но не восстановить сами записи.

Новые наборы появляются в существующем списке стендов веб-интерфейса.
Для запуска через веб нужны поднятые сервисы и пересобранный образ UI:

```bash
docker compose -f docker-compose.yml -f docker-compose.nosqli.yml \
  --profile ui up -d --build ui
```

Интерфейс: `http://localhost:8080`. Выбери набор с `NoSQLi profiles`.
Сервисы API уже запускает проверочный скрипт выше.
Второй API доступен отдельно на `http://localhost:3006/healthz`.

## Ограничения

- Проверка работает с известным JSON-контрактом и строковым значением поля.
- Нужны стабильные данные, уникальные ID и хотя бы одна запись с другим значением.
- Поля с массивами, пагинация, авторизация и формы других форматов пока не поддержаны.
- Настроенный маршрут должен только читать данные. POST сам по себе этого не гарантирует.
- Максимум 8 выбранных профилей, 4 запроса на профиль, 200 записей в ответе.
- Ответ ограничен 1 МиБ; таймаут сетевой операции — 5 секунд, чтение потока
  дополнительно проверяется по пределу 15 секунд.
- Переходы по редиректам отключены.
- Подтверждается изменение фильтра по контракту API. По HTTP-ответу нельзя
  достоверно определить конкретную СУБД или доказать выполнение произвольного кода.

Nuclei продолжает работать в прежних наборах. Наборы с `nosqli_profiles`
запускают отдельный Python-модуль сравнения JSON вместо Nuclei.
SAST-правила первого этапа не менялись.
