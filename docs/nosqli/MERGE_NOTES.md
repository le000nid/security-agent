# Слияние NoSQLi с командной веткой

Третий этап подготовлен от `feature/nosqli-portable-checks`, коммит `e7fa99e`.
Он включает предыдущие этапы по цепочке предков. Базу pull request нужно
выбирать по договорённости команды; автоматически сливать изменения не требуется.

При проверке обнаружена ветка `integration/v0.4.1-security-contours`,
коммит `4628d4f`. В ней уже есть три NoSQL-правила с теми же ID,
но с категорией `nosql-injection`. В нашей ветке категория — `injection`.

При разрешении конфликтов:

1. В `config/semgrep.yaml` оставить по одному правилу каждого ID.
   Для трёх существующих NoSQL-правил взять новые patterns/sources/sanitizers
   из третьего этапа. Добавить `javascript-nosqli-untrusted-pipeline` один раз.
   Остальные правила команды сохранить.
2. Согласовать `metadata.category`. При выборе командного `nosql-injection`
   обновить ожидания наших NoSQL-наборов в `config/expected/` и тестах,
   где явно ожидается `injection`. Механически менять категории остальных
   типов уязвимостей нельзя.
3. `app/semgrep.py` третьим этапом не меняется. Сохранить командные улучшения
   парсера; затем проверить совместимость наших verifier и сырых логов.
4. Объединить записи `config/benchmarks.yaml` по ID. Не заменять весь реестр
   нашей копией: в интеграционной ветке есть наборы других участников.
5. В тестах реестра объединить ожидаемые ID и разрешённые локальные хосты.
   Проверить, что `nosqli-sast-matrix` доступен в веб-API.
6. Сохранить упаковку `nosqli-sast-cases.json` и запуск нового скрипта в CI.

После слияния:

```bash
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
bash scripts/check-nosqli-sast.sh
bash scripts/check-nosqli.sh
bash scripts/check-nosqli-portable.sh
```

Проверка совместного набора правил выполнена отдельно: обновлённые
NoSQL-patterns объединены с правилами из `4628d4f` с сохранением категорий
существующих командных правил. Настоящий Semgrep прошёл нашу матрицу.
Правила других участников сохранены без изменений.

Это проверка совместимости правил, а не подтверждение полного слияния,
веб-запуска или CI всей интеграционной ветки. Эти проверки выполняются
после разрешения конфликтов и согласования категорий.


## Подготовленная версия объединения

Конфликты с `4628d4f` разрешены в отдельной рабочей ветке.
Точные решения, новый порт второго API и команды проверки записаны
в `INTEGRATION.md`. Перед отправкой этой ветки остаётся прогнать Docker
и проверить CI уже объединённого коммита.
