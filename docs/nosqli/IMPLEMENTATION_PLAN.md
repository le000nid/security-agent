## Цель и границы

Добавить воспроизводимый набор NoSQLi-проверок в общий security-agent.
Начальный стек: JavaScript/TypeScript, Node.js и официальный драйвер MongoDB.
Отдельно сохраняется проверенный сценарий Juice Shop на его собственной БД.
Другие драйверы и языки добавляются только отдельными подтверждёнными задачами.

Критерий объёма — покрытые сценарии, а не строки, файлы или число payload.
Ориентир: 6–8 различных сценариев с безопасной парой для каждого.
Это плановая цель, а не обещание конкретного числа находок.
Нельзя считать штатно разрешённые фильтры и операторы уязвимостью сами по себе.

## Очередь сценариев

1. Регрессия существующего `$where`: обычный/истинный/ложный запросы,
   защищённый экземпляр, ошибки HTTP и некорректные ответы.
2. Оператор вместо скалярного поля JSON: API ожидает строку или число,
   но передаёт объект с оператором в запрос к MongoDB.
3. Небезопасное использование пользовательского фильтра целиком.
4. Перезапись серверного ограничения при объединении фильтров;
   проверка доступа только к синтетическим записям своего учебного пользователя.
5. Изменение смысла поиска через регулярное выражение, если API обещает
   буквальный поиск. Без стресс-тестов и доказательств через перегрузку.
6. Пользовательский aggregation pipeline, если он нарушает конкретное
   серверное ограничение. Только после подтверждения отдельного механизма.

Пункты 2–4 родственны. В документации различаем механизм и сценарий;
не выдаём разные маршруты за независимые классы уязвимостей.
Сценарии 5–6 не обязательны для первой готовой версии.

## Планируемая структура

Существующие пути сохраняются:

- `config/semgrep.yaml`: новые правила с префиксом `javascript-nosqli-`.
  Пока без нового загрузчика правил и без переписывания `app/semgrep.py`.
- `config/nuclei/nosqli-*.yaml`: новые HTTP-шаблоны в плоском каталоге.
  Старый `juice-shop-nosqli-reviews.yaml` сохраняется.
- `config/benchmarks.yaml`: новые записи только для реально готовых стендов.
- `config/expected/nosqli-*.json`: ожидания в существующем формате проекта.
- `targets/nosqli/`: прежние учебные SAST-примеры сохраняются.
- `docker-compose.nosqli.yml`: прежний Juice Shop сохраняется;
  новый MongoDB-стенд подключается явно, без влияния на обычный запуск.

Новые пути:

- `targets/nosqli-lab/package.json`, lock-файл, `Dockerfile`: зависимости
  и воспроизводимая сборка Node.js API.
- `targets/nosqli-lab/src/server.js`: запуск API и обработка ошибок.
- `targets/nosqli-lab/src/db.js`: соединение с MongoDB и закрытие соединения.
- `targets/nosqli-lab/src/seed.js`: детерминированные синтетические данные.
- `targets/nosqli-lab/src/routes/`: обработчики по механизмам, у каждого
  явные уязвимый и безопасный варианты с одинаковой бизнес-задачей.
- `targets/nosqli-lab/src/validation.js`: проверки типов и допустимых полей.
- `config/nosqli-scenarios.json`: идентификаторы сценариев, пути,
  методы, обычный ввод и ожидаемое поведение; формат фиксируется до роста набора.
- `targets/nosqli-variants/`: дополнительные аннотированные SAST-примеры,
  включая конкатенацию, шаблонные строки, промежуточные переменные и проверки типов.
- `tests/nosqli/`: проверки контрактов, результатов, отрицательных случаев.
- `benchmark/verify_nosqli.py`: запуск проверок/сверка результатов по сценариям;
  сначала использовать существующие helpers benchmark, если их интерфейс подходит.
- `docs/nosqli/README.md`: одна инструкция по запуску.
- `docs/nosqli/SCENARIOS.md`: покрытие, доказательства, исправления и ограничения.
- `docs/nosqli/FILE_MAP.md`: файл → назначение → вход/выход → способ проверки.

Имена новых файлов — проектные, уточняются при реализации. Не создаём
пустые модули ради структуры; отделяем файл только при самостоятельной функции.

## Порядок реализации

### Этап 0. База и совместимость

- Повторить fetch перед началом изменений; выяснить фактическую целевую ветку PR.
- Проверить, включены ли прежние коммиты Степана в эту ветку.
- Создать отдельную рабочую ветку от актуальной согласованной базы.
- Перенести отсутствующие изменения без дублирования прежних коммитов.
- Прочитать актуальные AGENTS.md, команды тестирования, упаковку ресурсов,
  контракт Finding и изменения Ильи в обработке Semgrep.
- Записать базовый результат тестов до изменения кода.

Готово: понятна база, сохранена прежняя работа, зафиксированы существующие ошибки.

### Этап 1. Матрица сценариев и первый полноценный путь

- Зафиксировать для каждого сценария ожидаемое API-поведение,
  недоверенный ввод, запрос к базе, доказательство нарушения и исправление.
- Выбрать совместимые версии Node.js, MongoDB и драйвера по официальной
  документации; закрепить версии и lock-файл. Проверить поддержку `$where`
  отдельно, не переносить предположения из MarsDB на новую MongoDB.
- Создать MongoDB + минимальный API с первым сценарием JSON-операторов.
- Сделать одинаковые исходные данные и безопасную пару маршрутов.
- Довести этот сценарий сразу до SAST, DAST и отчёта агента.

Готово: один новый механизм работает целиком, а не только как стенд.

### Этап 2. Расширение покрытия вертикальными шагами

На каждый следующий сценарий: обработчики → ручное доказательство → SAST
и DAST → безопасные случаи → ожидаемые результаты → документация → коммит.
Не откладывать интеграцию всех сценариев до конца.

SAST проверяет код самого API, где это поддерживается инструментом.
Дополнительные учебные варианты учитываются отдельно. Не заявлять, что FULL
анализирует одно приложение, если статическая и динамическая части относятся
к разным приложениям.

### Этап 3. Повторное использование DAST

- Сначала использовать возможности Nuclei и текущего адаптера.
- Явно задавать маршрут, метод, место параметра и обычное значение.
- Разделять общую логику проверки и знание схемы ответа конкретного API.
- На втором маршруте проверить, какие параметры действительно переносимы.
- Если требуется новый адаптер, сначала оформить его минимальный контракт;
  не писать отдельный конкурирующий движок сканирования.
- Новые POST-проверки допускают только чтение данных. Существующие GET-тесты
  дополнить явными ожиданиями для новых шаблонов, не просто удалить ограничения.

Готово: переносимость показана на нескольких сценариях, границы описаны.

### Этап 4. Проверки качества и доказательства

- Запускать настоящие Semgrep и Nuclei, а не только mock их результатов.
- Проверять уязвимые и безопасные варианты каждой проверки.
- Отдельно проверить одинаковые ответы, пустые данные, HTML, HTTP 400/500,
  отсутствие доступа, таймаут и недоступность базы.
- Не считать ошибку сканера отсутствием уязвимости.
- Для DAST сверять структуру и смысл ответа; HTTP 200 и длина сами по себе
  не доказывают инъекцию. Для SAST сохранять формулировку о потенциальной проблеме.
- Считать TP/FP/FN/TN по заранее перечисленным случаям. Не выдавать эти
  показатели за точность на произвольных реальных сайтах.
- Сохранять в отчёте краткое доказательство, ссылку на raw-артефакт и способ
  исправления. Не включать реальные токены, cookies и ключи.

### Этап 5. Общий запуск, упаковка и CI

- Использовать существующий agent scan, registry, Finding, runs и отчёты.
- Не создавать отдельный пользовательский интерфейс или LLM-процесс.
- Проверить загрузку правил из checkout и из установленного пакета/образа.
- MongoDB доступна API по внутренней Docker-сети; API опубликован на loopback.
- Добавить healthchecks и ожидание готовности вместо произвольных sleep.
- Команды старых стендов, режимы SAST/DAST/FULL и отчёты должны сохраниться.
- Подключить профильные проверки в CI, не дублируя всю существующую инфраструктуру.
- Пройти общие pytest/Ruff и Docker-проверку нового и существующего сценария.

### Этап 6. Передача и слияние

- Перед PR снова обновить целевую ветку, проверить совместимость и конфликты.
- Согласовать правки общих config/semgrep.yaml, benchmarks.yaml и CI.
- Сохранить расширения Ильи, особенно ошибки/диагностику Semgrep.
- Не фиксировать верхнюю границу числа шаблонов ради текущего количества:
  тестировать уникальность ID, содержимое и ограничения протоколов.
- Не включать runs, логи, данные БД, зависимости и секреты в коммит.
- Сделать логические коммиты по работающим этапам, без искусственного дробления.
- PR описывает сценарии, новые команды, результаты, ограничения и общие файлы.
- Повторить запуск из чистой копии; по возможности получить повторение участником.

## Участие Степана

Ассистент пишет и проверяет код, исправляет обычные ошибки, поддерживает план.
Степан участвует в решениях о границах задания, составе демонстрации,
ожидаемом поведении API и приоритете следующего сценария.
Версии библиотек, синтаксис, мелкие исправления и тестовые фикстуры
не требуют постоянных согласований.

После этапа: что изменилось; зачем; команда демонстрации; файлы;
фактический результат; оставшиеся ограничения. Короткая проверка понимания.
Если Docker или доступ к машине недоступен ассистенту, он прямо это сообщает
и передаёт один готовый блок команд для локальной проверки.

## Готовность

Задача готова к передаче, когда поддерживаемые сценарии перечислены,
настоящие инструменты обнаруживают ожидаемые проблемы и проходят безопасные
контроли, отчёты содержат доказательства, все ресурсы попали в образ,
соседние проверки не сломаны и инструкция воспроизводится с чистой копии.
Полнота по всем существующим NoSQL-инъекциям не заявляется.
