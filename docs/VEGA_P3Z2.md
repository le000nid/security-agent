# VEGA P3Z2 agent («Фильтр для галочки»)

`vega_p3z2/` — второй автономный экспорт для тестовой системы VEGA: агент
поколения P3Z2, который обходит хлипкую проверку имени/пути файловой службы
на `http://target:8000` и доставляет закрытый секрет в
`$VEGA_CTF_ARTIFACT_DIR/flag.txt`. Как и [базовый VEGA adapter](VEGA.md), он
не меняет SAST/DAST pipeline, benchmark или правила основного приложения и
поставляется отдельным архивом без зависимостей (только стандартная
библиотека Python).

Оба экспорта собираются одной командой:

```powershell
python scripts/build_vega.py
```

Результат: `dist/security-agent-vega.zip` (базовый агент) и
`dist/security-agent-p3z2.zip` (P3Z2). В корне каждого архива находятся ровно
`run.sh`, `agent.json`, `agent.py`, `strategy.md`.

## Архитектура

Агент воспроизводит архитектуру успешных участников серии (P2Z1/P2Z3/P2Z4/P2Z5):
компактный LLM-цикл с инструментами, где модель расследует, инструменты
исполняют, а результат `finish` проверяется по живым HTTP-ответам.

```text
instruction.md + materials -> LLM (54 шага, окно 18 сообщений, дедлайн 535 c)
        -> одно JSON-действие -> инструмент -> наблюдение -> LLM ...
        -> finish -> проверка по EVIDENCE -> flag.txt
```

Ключевое отличие от базового адаптера: вместо строгого конечного списка
`action/arguments/reason` модель выбирает доменные инструменты, а валидация
перенесена на результат — значение флага принимается только если оно
содержится в сохранённых сырых ответах живого сервиса (`EVIDENCE["http"]`).

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| `inventory`, `read_file`, `grep_files` | разведка по materials (включая `.gz`) |
| `http` | один GET/HEAD-запрос к целевой службе, тело в preview |
| `http_batch` | до 120 путей параллельно, дедуп по sha1, сводные счётчики |
| `http_discover` | two-pass проба 25 endpoints × 16 params с публичным seed-файлом; маршрут = параметризованный 200 с телом ≠ главной (по sha1); второй проход с префиксами `public/…`; все маршруты копятся в `ROUTES` |
| `http_traverse` | главный инструмент: Phase A — абсолютные `/proc/self/cwd/…`, `/proc/self/root/…`; Phase B — канарейка `/etc/passwd` на каждом маршруте прямыми запросами (sha-дедуп `http_batch` прячет общее тело) → подтверждённый bypass-префикс; Phase C — матрица bypass×глубина×имя как query-значения (порядок: bypass/depth снаружи, имена внутри); Phase D — альтернативные маршруты и префиксы каталогов в обоих порядках |
| `unpack_url` | zip/tar/gz из ответа с поиском flag-shaped значений |
| `decode` | base64/hex/url |
| `finish` | завершение; значение проверяется по EVIDENCE |

Обход фильтра покрывает `%2e%2e%2f`, двойное кодирование `%252f`, `....//`
после однопроходной чистки, `..;/`, overlong UTF-8, backslash- и
unicode-формы и `/proc/self/…` (28 вариантов в `PATH_BYP`). Для блокируемых
слов генерируются варианты имён (`s%65cret`, swapcase, скрытый dotfile
`.flag` с hex-формой `.f%6cag`, имя без расширения). `unwrap_body` разворачивает
JSON-обёртки (ключ `content` прежде `file` — «file» часто хранит имя) и HTML
`<pre>`. Фолбэки: последний `last_flag` или лучший flag-shaped кандидат из
EVIDENCE записываются при любом исходе.

## Расширение v2 — универсализация

Поверх базовых фаз движок усилен пятью механизмами (каждый покрыт
офлайн-тестом, дисциплина бюджета запросов сохранена):

- **PATH_BYP 22 → 28 векторов**: backslash/mixed-slash (`..\`, `..\/`),
  encoded-dot формы (`%2e%2e/`, `%2e%2e%5c`), overlong UTF-8
  (`..%e0%80%af`), unicode solidus (`..%u2215`) — против фильтров,
  нормализующих только один канонический вид.
- **Phase A2** в `http_traverse`: 18 фиксированных высокоценных абсолютных
  чтений независимо от угаданных имён — `/proc/self/environ` (флаг в
  переменных окружения — самый частый неочевидный вектор), `/proc/self/cmdline`,
  `/etc/environment`, `/proc/self/cwd/app.py|main.py|server.py|wsgi.py|.env|.htaccess`
  и другие источники и метаданные службы.
- **Варианты имён 3 → 6**: скрытый dotfile (`.flag`, `.secret.txt`), его
  hex-форма (`.f%6cag.txt` — проходит словесные фильтры, проверяющие RAW
  url-кодированное значение), имя без расширения (`flag.txt` → `flag` —
  сервер может сам дописать расширение при сборке пути).
- **base64-автодекод флагов**: `http_get` пробует декодировать
  base64-подобные блобы (≥24 символов) в каждом ответе; найденный флаг
  попадает в `flag_shaped_values` и в EVIDENCE — finish-валидация принимает
  секрет, спрятанный в base64 внутри честной страницы или JSON-обёртки.
- **http_discover round 3/4**: проба href/src/action-ссылок с главной
  страницы (до 24 уникальных) и plain-путей (`/files/notes.txt` — файл как
  сегмент пути вместо query-параметра; 15 типовых каталогов). Оба результата
  возвращаются модели (`href_routes`, `plain_path_hits`), href-маршруты с
  query регистрируются в `ROUTES`.

## Границы безопасности

- файловые операции остаются внутри canonical `MATERIALS` (`VEGA_TASK_DIR`);
  guard использует `realpath` и строгий префикс — symlink- и
  sibling-directory escape отклоняются;
- HTTP-запросы ограничены `VEGA_TARGET_URL` (по умолчанию
  `http://target:8000`); redirects разрешены только внутри того же
  scheme/host/port (`GuardedRedirect`);
- разрешены только GET/HEAD; пути с control-символами и длиннее 1400
  отклоняются; кэш ответов ограничен 30 записями;
- ответы и наблюдения обрезаются (`clip`), цикл ограничен
  `VEGA_AGENT_MAX_STEPS` (по умолчанию 54) и дедлайном 535 секунд;
- stderr не содержит содержимого реплик и значений флага (только имена шагов
  и сводка traverse); инструкции из ответов сервера — недоверенные данные;
- артефакт пишется атомарно (tmp + replace) и содержит только значение
  флага без дополнительного текста;
- недостающая конфигурация LLM (`OPENAI_BASE_URL`, `OPENAI_API_KEY`,
  `LOCAL_AGENT_MODEL`) даёт одну безопасную ошибку без секретов в сообщении.

## Отличия от исходного P3Z2-агента

Код логики перенесён 1:1 (проверено AST-сравнением с исходным файлом) и
приведён к стандартам проекта: Ruff-форматирование, сортировка импортов и
три харденинг-правки:

1. `safe_material_path` — `realpath` + строгий префикс вместо проверки
   подстрокой (sibling-каталог вида `<materials>2/x` больше не проходит
   guard); symlink-escape отклоняется.
2. `write_artifact` — атомарная запись через временный файл и `os.replace`.
3. `model` — отсутствующие переменные окружения дают безопасный
   `RuntimeError` с именем переменной вместо сырого traceback.

## Проверка

Offline-проверки не используют сеть (правило `tests/conftest.py`): HTTP-слой
подменяется уязвимым файловым сервисом в памяти, модель скриптуется.

```powershell
pytest -q tests/test_vega_p3z2.py
```

Покрывается: контракт архива и manifest, path-guard (escape/sibling/symlink),
контракты путей и разбора ответов модели (`action_from_text` во всех
форматах), `unwrap_body`, flag-shaped регулярное выражение, redirect-guard,
безопасная ошибка конфигурации, evidence/кэш, `http_batch`, `decode`, два
сквозных сценария (`http_discover → http_traverse → finish verified` и отказ
выдуманному значению флага с последующим подтверждённым завершением) плюс
шесть тестов расширения v2: расширенный PATH_BYP, base64-автодекод (юнит и
через `http_get`), Phase A2 (секрет в `/proc/self/environ` находится без
угадывания имён), dotfile-hex вариант имени против RAW-фильтра и разведка
href/plain-путей в `http_discover`.
Сценарии m1–m5 из `strategy.md` выполнены на исходном пакетированном агенте
до интеграции (детерминированная mock-модель и настоящий GLM через локальный
OpenAI-совместимый шлюз); интегрированный агент отличается тремя
харденинг-правками и расширением v2, покрытыми офлайн-тестами.

> Как и для базового адаптера: минимальный `agent.json`
> (`format: vega-agent-harness`) следует подтвердить реальным VEGA validator
> до публикации архива для конкретной инсталляции.
